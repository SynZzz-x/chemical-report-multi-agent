# 阻塞处理动作交互设计

## 目标

当工作流进入 `needs_user_input` 时，用户直接在阻塞处理区完成恢复操作，不再需要先选动作、再到聊天框发送“确认”。普通聊天输入保持不变。

## 交互

- `AUTHORIZE_WEB`：显示“授权并继续”按钮，点击后直接恢复工作流。
- `ACCEPT_EVIDENCE_GAP`：显示“接受并继续”按钮，点击后直接恢复工作流。
- `ADJUST_REQUIREMENT`：显示专用文本框和“提交新要求”按钮；空文本不可提交。
- `UPLOAD_RESOURCES`：显示专用多文件上传区和“上传并继续”按钮；未选择文件不可提交，支持 `csv/pdf/docx/txt/md`。

动作标签仍由阻塞 payload 的 `accepted_choices` 决定，界面不得展示后端未授权的动作。

## 状态流

专用控件生成统一的提交对象，由现有文件保存、消息记录、`Command(resume=resume_payload)`、流式执行和任务状态更新链处理。提交后先清除当前 `pending_interrupt`；如果图再次中断，再写入新的阻塞信息。组件 key 绑定当前任务和阻塞内容，避免恢复历史任务时复用旧输入。

## 错误与可观测性

- 缺少动作所需输入时只提示，不恢复图。
- 文件保存或图执行失败沿用现有错误处理。
- 用户消息记录包含所选动作及必要的文本/附件名称，确保历史任务可审计。

## 测试

- 纯函数测试四种动作的提交要求、默认恢复文本和展示标签。
- 源码集成测试确认专用表单存在，且不再通过聊天输入传递 `pending_resume_action`。
- 运行相关恢复测试与完整非环境性回归测试。
